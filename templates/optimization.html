📘 Important Viva Note: SQLite Cost-Based Optimizer (CBO) Behavior

In relational database management systems like SQLite, the Cost-Based Optimizer evaluates the estimated disk I/O cost before choosing an execution plan. For very small tables (e.g. under 50 rows), reading the entire table directly in a sequential scan is often faster than reading an index page into memory and then reading the table data page. When tables grow into thousands of rows, the optimizer switches decisively to SEARCH TABLE ... USING INDEX, delivering order-of-magnitude performance gains.

🎓 College Viva & Presentation Preparation Guide

Key DBMS and Query Optimization questions frequently asked by professors and external examiners.

1. What is the difference between a table scan (SCAN) and an index lookup (SEARCH)?
In a table scan (SCAN TABLE), the database engine must inspect every single row in the table from beginning to end ($O(N)$ time complexity). In an index lookup (SEARCH TABLE USING INDEX), the database traverses a balanced B-Tree structure directly to the matching key ($O(\log N)$ time complexity), drastically reducing disk I/O and CPU cycles.
2. What is a Composite Index, and how did you use it in this project?
A Composite Index is an index defined on multiple columns, such as CREATE INDEX idx_product_category_rating ON products(category, rating DESC). In our project, when a user browses a category sorted by top ratings, SQLite uses this composite index to simultaneously filter by category = ? and return the rows in pre-sorted order by rating DESC. This completely eliminates the need for SQLite to create a temporary in-memory B-Tree to perform a separate sorting pass (USE TEMP B-TREE FOR ORDER BY).
3. Why does SQLite sometimes choose a full table scan even when an index exists?
SQLite utilizes a Cost-Based Optimizer (CBO). If a table is small (e.g. 15 to 50 rows), the entire table fits into a single 4096-byte database page in memory cache. Reading that single page linearly is faster than traversing index B-Tree pages and then performing random page lookups on the table. Once the dataset scales (demonstrated via our 5,000 row generator), the cost of scanning outweighs index traversal, and the optimizer switches to the index.
4. Why are Parameterized Queries critical for both optimization and security?
Optimization: Parameterized queries (using ? placeholders) allow the database engine to parse and compile the SQL execution plan once, and cache it for subsequent executions with different parameter values (prepared statements).
Security: They treat user input strictly as literal values rather than executable SQL code, completely neutralizing SQL Injection attacks.
5. What does SARGable mean in SQL query design?
SARGable stands for Search Argument Able. A query predicate is SARGable if the database engine can directly exploit an index to satisfy it. Wrapping indexed columns in functions or math expressions (e.g., WHERE (price + 0) <= 2000 or WHERE category LIKE '%Books%') renders the condition non-SARGable, forcing a full table scan. Writing WHERE price <= 2000 is SARGable and uses the B-Tree index.
